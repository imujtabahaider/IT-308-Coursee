Publishing Android Applications

Learn how to prepare, test, package, sign, and distribute Android applications so that users can install and use them.

24.1 Introduction to Android Application Publishing

Android application development does not end when the developer finishes writing code.

After developing an application, the developer must prepare it so that other people can install and use it on their Android devices.

This complete process is called Android application publishing.

Definition:

Android application publishing is the process of preparing, testing, packaging, signing, and distributing an Android application so that users can install and use it.

Example

Suppose you develop a student management application.

Your application contains:

  • Student registration.
  • Login and logout.
  • Student records.
  • Attendance management.
  • Examination results.
  • Teacher information.

You have completed the application in Android Studio. However, other students cannot automatically install it just because you have written the code.

You must prepare a release version, generate an application package, sign it, and distribute it.

You can distribute the application through:

  • Google Play Store.
  • Other Android application stores.
  • Your university website.
  • Your own website.
  • Direct APK sharing.
24.1.1 Why Is Application Publishing Important?

Application publishing is important for several reasons:

  1. Application distribution: It makes an application available to users.
  2. User access: Users can download and install the application on their devices.
  3. Business opportunities: Developers can sell applications or earn money through advertisements and in-app purchases.
  4. Public availability: An application can reach users in different countries.
  5. Updates: Developers can release new versions to fix problems and introduce features.
  6. Professional development: Publishing an application provides practical experience of real-world software development.

24.2 Development Version vs Release Version

During Android application development, developers generally work with two important versions:

  1. Development version (Debug version).
  2. Release version.

Both versions contain the application, but they are prepared for different purposes.

24.2.1 Development Version (Debug Version)

A development or debug version is used while developing and testing an application.

Developers use it to find programming errors, test features, and check whether the application works correctly.

Example

For example, while developing a login application, you may need to check:

  • Whether the login button works.
  • Whether the password is correct.
  • Whether data is saved.
  • Whether the application connects to the database.
  • Whether errors occur.

A debug version helps developers perform these activities.

Characteristics:

  • Mainly used during development.
  • Contains debugging support.
  • Can include additional debugging information.
  • Usually signed automatically with a debug certificate by Android Studio.
  • Not intended as the final public release.
24.2.2 Release Version

A release version is the final prepared version of an application that is intended for distribution to users.

Before generating it, developers check the application, configure its release settings, and prepare its signing credentials.

Example

For example, after completing and testing your student management application, you generate its release version so students and teachers can install it.

Characteristics:

  • Prepared for distribution.
  • Signed using a release signing key.
  • Usually optimized for production.
  • Should not expose debugging information or development credentials.
  • Can be uploaded to an app store.
24.2.3 Difference Between Debug and Release Versions
Debug Version Release Version
Used during development. Used for distribution.
Helps developers find errors. Intended for actual users.
Usually signed with a debug certificate. Signed with a release signing key.
May contain debugging support. Debugging support should be disabled as appropriate.
Not intended for public production use. Prepared for production use.

24.3 Preparing an Application for Publishing

Before publishing an Android application, developers must prepare it carefully.

An application should not be published immediately after writing its code.

It must be checked to ensure that it works correctly, provides a good user experience, and follows Android security requirements.

24.3.1 Important Preparation Steps
24.3.2 Complete Application Development

First, developers must complete all the required features.

Example

For example, a student management application may require:

  • Login system.
  • Student registration.
  • Student dashboard.
  • Attendance records.
  • Examination results.
  • Database connection.

All essential features should be implemented before release.

24.3.3 Remove Unnecessary Code

During development, programmers may write temporary code for testing.

For example:

System.out.println("Testing application");

They may also create temporary buttons, test screens, or sample records.

Before publishing, developers should remove unnecessary development code and testing components.

24.3.4 Check Application Permissions

Android applications request permissions when they need access to protected device features.

Examples include:

  • Camera.
  • Location.
  • Contacts.
  • Microphone.
  • Notifications.

Developers should request only the permissions that their application actually needs.

Example

For example, a calculator application does not normally need access to the user's contacts or location.

24.3.5 Check Application Name and Icon

The application should have a meaningful name and a professional icon.

For example:

  • Application name: Student Manager.
  • Icon: A suitable student or education-related design.

The name and icon help users recognize the application.

24.3.6 Configure Application Settings

Developers should check important configuration settings, including:

  • Application ID (package name).
  • Minimum Android version.
  • Target Android version.
  • Version code.
  • Version name.
  • Release signing configuration.

We will explain these settings in detail in the following sections.

24.3.7 Check Internet and Database Connections

If the application uses online services, developers should verify that:

  • API URLs are correct.
  • Server connections work.
  • Database operations work.
  • Error messages are handled properly.
  • Sensitive information is protected.
Important:

Never include secret API keys, passwords, or database administrator credentials directly in an application package.

24.4 Application Testing and Debugging

Before publishing, an application must be tested to ensure that it works correctly.

Application Testing:

Application testing is the process of checking an application to identify errors, verify features, and ensure that it behaves as expected.

Debugging:

Debugging is the process of finding and correcting errors in an application.

24.4.1 Types of Application Testing
24.4.2 Functional Testing

Functional testing checks whether application features work according to their requirements.

Example

In a student management application:

  • Does registration work?
  • Does login work?
  • Can students view their results?
  • Can teachers update attendance?

If a feature does not work correctly, the developer must fix it.

24.4.3 UI Testing

UI stands for User Interface.

UI testing checks whether the application's screens and controls work correctly.

It includes:

  • Buttons.
  • Text fields.
  • Images.
  • Menus.
  • Navigation.
  • Screen layouts.

For example, developers check whether buttons are visible and whether text fits properly on different screen sizes.

24.4.4 Compatibility Testing

Compatibility testing checks whether an application works on different Android devices and versions.

For example:

  • Android 12.
  • Android 13.
  • Android 14.
  • Android 15.

Developers should also consider different screen sizes, device manufacturers, and hardware capabilities.

24.4.5 Performance Testing

Performance testing checks how efficiently an application operates.

It includes checking:

  • Application loading speed.
  • Memory consumption.
  • CPU usage.
  • Battery consumption.
  • Network performance.
24.4.6 Security Testing

Security testing checks whether an application protects user information and prevents unauthorized access.

For example:

  • Is user information protected?
  • Is communication encrypted using HTTPS?
  • Are passwords handled securely?
  • Can unauthorized users access restricted features?
24.4.7 Testing Tools
Tool Purpose
Android Emulator Tests applications on virtual Android devices.
Physical Android Device Tests applications on real hardware.
Logcat Displays application logs and error messages.
Android Studio Debugger Helps find and investigate programming errors.
JUnit Supports unit testing.
Espresso Supports Android UI testing.
24.4.8 Why Is Testing Necessary Before Publishing?

Testing is necessary because an application may contain errors that were not noticed during development.

If an application is published without proper testing:

  • It may crash.
  • Buttons may not work.
  • User information may be lost.
  • It may not work on some devices.
  • Users may uninstall it because of poor performance.

Therefore, proper testing is an essential part of application publishing.

24.5 Application Versioning

Application versioning means assigning version information to different releases of an application.

It helps developers identify application versions and manage updates.

Android mainly uses two important version properties:

  1. versionCode
  2. versionName
24.5.1 versionCode

versionCode is an integer value used internally by Android to identify application versions.

It helps Android determine whether an installed application can be updated with a new version.

Example:

versionCode 1

When you release a new version, you increase the value:

versionCode 2

Then:

versionCode 3
Important:

A new update must have a higher version code than the previously published version. Google Play also applies version-code requirements and limits.

24.5.2 versionName

versionName is a human-readable version number displayed to users or used by developers.

Example:

versionName "1.0"

A later version might be:

versionName "1.1"

Another version might be:

versionName "2.0"
24.5.3 Example of Versioning
Application Release versionCode versionName
First release 1 1.0
Second release 2 1.1
Third release 3 1.2
Major update 4 2.0
24.5.4 Difference Between versionCode and versionName
versionCode versionName
Integer value. Human-readable version string.
Used internally for version comparison. Used to identify the version for people.
Must increase for a new update. Can follow a developer-defined naming scheme.
Not normally displayed to users. Can be displayed to users.
24.5.5 Where Are These Settings Configured?

In a modern Android project, these values are generally configured in the app module's build.gradle or build.gradle.kts file.

Groovy example:

android {

    defaultConfig {

        applicationId "com.example.studentmanager"

        minSdk 23

        targetSdk 35

        versionCode 1

        versionName "1.0"

    }
}

This is an illustrative configuration. The appropriate SDK versions depend on the project's requirements and current publishing policies.

24.6 Android Application Package Formats: APK and AAB

After developing and testing an application, developers must package it into a format that can be distributed.

Android provides two important package formats:

  1. APK (Android Package Kit).
  2. AAB (Android App Bundle).
24.6.1 APK (Android Package Kit)

An APK is an Android application package that contains the files required to install and run an Android application.

It is an installable file.

For example:

StudentManager.apk

When a user installs this APK, Android uses the package to install the application on the device.

An APK can contain:

  • Compiled application code.
  • Application resources.
  • Images and icons.
  • XML files.
  • Application manifest.
  • Other required application files.

Advantages of APK:

  1. Can be installed directly on compatible Android devices.
  2. Can be shared through websites or other distribution methods.
  3. Useful for testing and manual distribution.
  4. Can be generated for different release configurations.
24.6.2 AAB (Android App Bundle)

An Android App Bundle is a publishing format that contains the compiled code and resources of an Android application.

Its file extension is:

.aab

For example:

StudentManager.aab

Unlike an APK, an AAB is not normally installed directly by the user.

Instead, developers upload the AAB to Google Play. Google Play uses it to generate optimized APKs suitable for different devices.

For example, different devices may require different:

  • Screen-density resources.
  • Language resources.
  • Device-specific configuration resources.

Google Play can deliver the appropriate components to each device.

24.6.3 Difference Between APK and AAB
APK AAB
Installable Android package. Publishing package format.
Can be installed directly on a device. Normally uploaded to Google Play for processing.
Contains resources and code packaged for installation. Contains code and resources from which optimized APKs can be generated.
Can be shared for direct installation. Not normally installed directly by users.
Commonly used for testing and direct distribution. Used for Google Play publishing.
Important:

Google Play requires new applications to be published using the Android App Bundle format, subject to applicable platform requirements. Developers can still generate APKs for testing and other distribution methods.

24.7 Generating a Signed APK or Android App Bundle

After preparing and testing an application, developers generate a release package.

In Android Studio, this can be done through the Generate Signed Bundle / APK option.

24.7.1 Steps
Step 1: Open Android Studio

Open your completed Android project.

Step 2: Open the Build menu

From the top menu, select:

Build → Generate Signed Bundle / APK
Step 3: Select the package format

Android Studio displays two options:

  • Android App Bundle.
  • APK.

Select the required format.

For Google Play publishing, Android App Bundle is generally the preferred option.

Step 4: Create or select a keystore

Android Studio asks you to provide signing information.

A keystore is a file that stores the key information used to sign your application.

If you are publishing for the first time, you may need to create a new keystore.

Step 5: Enter signing information

Provide the required details, such as:

  • Keystore path.
  • Keystore password.
  • Key alias.
  • Key password.
Step 6: Select the release build variant

Choose:

release

This generates a production release package rather than a debug build.

Step 7: Generate the package

Click Finish or Generate.

Android Studio builds the signed application package.

24.7.2 Output

Depending on your selection, Android Studio generates:

app-release.apk

or:

app-release.aab

The exact output location depends on your Android Studio project configuration.

Important:

Keep your release signing credentials secure. Losing access to the signing key can create serious problems when releasing future updates, depending on your signing arrangement.

24.8 Application Signing and Digital Certificates

Application signing is an important security step in Android application publishing.

Definition:

Application signing is the process of using a digital signing key to establish the authenticity and integrity of an application package.

In simple words, signing helps establish that an application update comes from the expected developer and that the signed package has not been modified after signing.

24.8.1 Why Is Application Signing Important?
  1. Application authenticity: Helps identify the developer or signing identity associated with an application.
  2. Application integrity: Helps detect changes made to a signed package.
  3. Update management: Android uses signing identity to enforce application update compatibility.
  4. Security: Helps prevent unauthorized replacement of an application with a differently signed package.
24.8.2 What Is a Keystore?

A keystore is a file that stores cryptographic keys and related certificates.

Developers use it to sign Android applications.

For example:

my-release-key.jks

This file may contain a signing key and its associated certificate.

24.8.3 Important Signing Terms
Term Meaning
Keystore File that stores signing keys and certificates.
Key Cryptographic material used for signing.
Key Alias Name used to identify a particular key in a keystore.
Password Protects access to the keystore or key.
Digital Certificate Contains information associated with the signing identity.
Digital Signature Cryptographic proof used to verify package integrity and signing identity.
24.8.4 What Is Google Play App Signing?

Google Play App Signing is a service that helps manage application signing for Google Play distribution.

Under this system:

  • The developer uploads an app bundle or APK signed with an upload key.
  • Google Play verifies the upload.
  • Google Play uses the app-signing key to sign the APKs delivered to users.

The upload key and app-signing key serve different purposes.

Important:

Never share your private signing keys or passwords publicly, and always maintain secure backups.

24.9 Release Configuration

Before generating the final release package, developers configure the application for production.

This process is called release configuration.

It ensures that the application is prepared for real users rather than development testing.

24.9.1 Important Release Settings

1. Application ID

The application ID uniquely identifies an Android application on the device and in app distribution systems.

Example:

applicationId "com.example.studentmanager"

Once an application is published, changing its application ID generally means it is treated as a different application.

2. Minimum SDK

The minimum SDK determines the oldest Android API level supported by the application.

For example:

minSdk 23

This means the application requires at least Android API level 23.

3. Target SDK

The target SDK indicates the Android API level against which the application is designed and tested.

It also affects certain Android compatibility behaviors.

Example:

targetSdk 35

Developers must keep this setting aligned with current Google Play requirements.

4. Version Information

Developers configure:

versionCode 1
versionName "1.0"

5. Release Signing

The application must be signed using the appropriate release signing arrangement.

6. Debugging Configuration

Development-only debugging features and sensitive test information should not be exposed in the production release.

24.10 Security and Performance Checks

Before publishing an application, developers should perform final security and performance checks.

24.10.1 Security Checks
  • Use HTTPS for secure network communication.
  • Do not store passwords in plain text.
  • Do not hardcode sensitive credentials in application code.
  • Request only necessary permissions.
  • Validate user input.
  • Protect private user information.
  • Use secure authentication and authorization methods.
24.10.2 Performance Checks
  • Reduce unnecessary application size.
  • Optimize images and other resources.
  • Avoid unnecessary background processing.
  • Check memory consumption.
  • Reduce unnecessary network requests.
  • Check application startup time.
  • Test on different devices.
Example

Suppose your application contains 20 large images, but only five are actually required.

You should remove unnecessary resources and optimize the remaining images.

This can reduce the application size and improve performance.

24.11 Preparing Application Information and Resources

A professional application requires more than its executable package.

Developers should also prepare the information and resources needed to present the application to users.

Common resources include:

  1. Application name.
  2. Application icon.
  3. Short description.
  4. Full description.
  5. Screenshots.
  6. Feature graphic, where required.
  7. Privacy policy, where applicable.
  8. Contact information.
  9. Support website or email.
  10. App category.
Example

For example, a student management application might have:

  • Name: Student Manager.
  • Category: Education.
  • Description: Manage student records, attendance, and examination results.
  • Screenshots: Login page, dashboard, attendance screen, and result screen.

These resources will be used when creating the application listing on an app store.

24.12 Publishing Process and Post-Release Updates

After completing the preparation steps, the application is ready for distribution.

The general publishing process is:

  1. Complete application development.
  2. Test the application.
  3. Configure release settings.
  4. Generate a signed release package.
  5. Prepare application information and resources.
  6. Upload the application to the selected distribution platform.
  7. Complete the platform's required declarations and checks.
  8. Submit for review if required.
  9. Release the application.
  10. Monitor feedback and fix problems.
24.12.1 What Happens After Publishing?

Publishing does not mean that the developer's work is finished.

Developers must continue maintaining the application.

Post-release activities include:

  • Fixing bugs.
  • Improving performance.
  • Adding new features.
  • Updating security.
  • Supporting newer Android versions.
  • Responding to user feedback.
  • Releasing new application versions.
24.12.2 Example

Suppose you publish Student Manager version 1.0.

Users report that the attendance screen sometimes crashes.

You fix the problem and prepare version 1.1.

You increase the version code and publish the update.

Users can then receive the updated application through the distribution platform.

24.13 Advantages and Challenges of Android Application Publishing

24.13.1 Advantages
  1. Wider reach: Applications can reach users around the world.
  2. Business opportunities: Developers can generate revenue.
  3. Easy distribution: Users can install applications through supported distribution platforms.
  4. Professional experience: Developers gain practical software-release experience.
  5. Application updates: Developers can improve their applications after release.
  6. User feedback: Developers can receive reviews and suggestions.
24.13.2 Challenges
  1. Testing requirements: Applications need extensive testing before release.
  2. Security requirements: Developers must protect application and user data.
  3. Store policies: Applications must follow distribution-platform policies.
  4. Device compatibility: Applications may behave differently on different devices.
  5. Maintenance: Developers must regularly fix bugs and provide updates.
  6. Review process: App stores may reject applications that violate their requirements.

Deployment on App Stores

Understand how Android applications are prepared, uploaded, tested, reviewed, and released through Google Play and other application distribution platforms.

21.1 Introduction to App Store Deployment

After developing and publishing an Android application package, the next step is to make the application available to users.

This process is called app store deployment.

Definition:

App store deployment is the process of uploading, configuring, reviewing, and releasing a mobile application through an application distribution platform so that users can download and install it.

An app store acts as a platform between application developers and users.

Developers upload their applications to the store, and users can search for, download, install, and update them.

Examples of Android App Stores
  1. Google Play Store.
  2. Samsung Galaxy Store.
  3. Amazon Appstore.
  4. Huawei AppGallery.
  5. Xiaomi GetApps.
How does app store deployment work?

Suppose you develop a student management application.

The general process is:

  1. Complete application development.
  2. Test the application.
  3. Generate a signed Android App Bundle.
  4. Create a developer account on an app store.
  5. Create an application listing.
  6. Upload the application package.
  7. Complete the required declarations.
  8. Submit the application for review.
  9. Release the approved application.
  10. Users download and install it.
Why is app store deployment important?
  • It makes applications accessible to users.
  • It provides a centralized application distribution platform.
  • It allows users to discover applications through search.
  • It helps developers distribute updates.
  • It provides application ratings and reviews.
  • It supports different application monetization methods.

Developers use the Google Play Store to distribute their applications to Android users.

21.4 Creating a Google Play Console Developer Account

Before publishing an application on Google Play, a developer needs a Google Play Console developer account.

Definition:

A developer account is an account that allows an individual or organization to manage applications, upload releases, and publish applications through Google Play.

Steps to create an account

Step 1: Open Google Play Console

Visit:

Google Play Console

Step 2: Sign in

Sign in using your Google account.

Step 3: Register as a developer

Follow the registration instructions and select the appropriate account type.

The available account types include:

  • Personal account: For an individual developer.
  • Organization account: For a business, company, or other organization.

Step 4: Provide required information

Google may request information such as:

  • Developer name.
  • Contact email address.
  • Contact phone number.
  • Country or region.
  • Identity verification information.
  • Organization details, when applicable.

Step 5: Pay the registration fee

Google Play Console currently requires a one-time registration fee for a developer account. The amount and payment requirements should be checked during registration.

Step 6: Complete verification

Complete the identity and other verification steps required for your account type.

Step 7: Access the dashboard

After registration and the required verification, you can access the Play Console dashboard and manage your applications.

Important points
  • A developer account is required to publish applications on Google Play.
  • Developers must provide accurate information.
  • Google may require additional verification.
  • Personal and organization accounts can have different testing and verification requirements.
  • Creating an account does not automatically approve an application for publication.

21.5 Creating an Application in Google Play Console

After creating a developer account, the next step is to create an application entry.

This entry represents your application inside Google Play Console.

Steps

Step 1: Open the Play Console dashboard

Sign in to your developer account.

21.6 Preparing a Store Listing

A store listing is the information page that users see when they open an application on Google Play.

It explains what the application does and helps users decide whether they want to install it.

A good store listing should provide clear, accurate, and useful information.

Main elements of a store listing
21.6.1 Application Name

The application name is the name displayed to users.

Example:

Student Manager

It should be meaningful and easy to recognize.

21.6.2 Short Description

A short description briefly explains the application's main purpose.

Example:

Manage student records, attendance, and examination results easily.

It helps users quickly understand what the application offers.

21.6.3 Full Description

The full description explains the application's features and functionality in more detail.

Example:

Student Manager

Student Manager is an application designed to help educational institutions manage student information.

Main features:

  • Student registration.
  • Attendance management.
  • Examination results.
  • Student profiles.
  • Teacher information.
  • Academic records.
21.6.4 Application Icon

The application icon is the visual symbol that represents the application.

It appears in search results, application listings, and on users' devices.

21.6.5 Screenshots

Screenshots show users what the application looks like.

For example, you might provide screenshots of:

  • Login screen.
  • Dashboard.
  • Student registration page.
  • Attendance screen.
  • Result screen.
21.6.6 Feature Graphic

A feature graphic is a promotional image used in supported Google Play placements.

It visually represents the application and its purpose.

21.6.7 Category

The category identifies the type of application.

For example:

  • Education.
  • Business.
  • Productivity.
  • Finance.
  • Entertainment.
21.6.8 Contact Information

Developers provide appropriate contact details so users can reach them for support.

This may include:

  • Support email.
  • Website.
  • Other required contact details.
Why is a store listing important?

A store listing is important because it:

  1. Introduces the application to users.
  2. Explains its features.
  3. Shows its user interface.
  4. Helps users understand its purpose.
  5. Improves application discoverability.
  6. Provides support information.

21.8 App Content and Policy Declarations

Before Google Play makes an application available, developers must provide information about the application's content, permissions, privacy practices, and other relevant details.

These declarations help Google evaluate whether the application follows its policies and legal requirements.

They are managed through the App content section of Play Console.

21.8.1 Privacy Policy
Definition:

A privacy policy is a document explaining how an application collects, uses, stores, and shares users' information.

For example, a student management application may collect:

  • Student names.
  • Email addresses.
  • Profile pictures.
  • Attendance records.

Its privacy policy should explain how this information is handled.

Google Play requires privacy-policy information for relevant applications, including applications targeting children and applications handling personal or sensitive user data. Check the current requirements for your application's situation.

21.8.2 Data Safety Section

The Data safety section explains how an application handles user data.

Developers must accurately declare:

  • What data the application collects.
  • Whether data is shared with other parties.
  • How collected data is used.
  • Whether data is encrypted in transit.
  • Whether users can request data deletion, where applicable.

For example, if an application collects a user's email address and shares it with a service provider, its declaration must accurately reflect that practice.

Even applications that do not collect or share user data may still need to complete the Data safety form and provide a privacy policy, subject to applicable exemptions.

21.8.3 Advertisement Declaration

Developers must declare whether their application contains advertisements.

For example:

  • Banner advertisements.
  • Video advertisements.
  • Advertisements displayed through third-party advertising SDKs.
  • Native advertisements.

If the application contains ads, Google Play can display a relevant advertisement label on its listing.

21.8.4 Content Rating

Content rating describes the suitability of an application for different age groups.

For example, an educational application for children should accurately describe its content and intended audience.

Developers answer the required questionnaire, and the application receives the applicable content rating.

21.8.5 Target Audience

Developers must declare the intended audience of their application.

For example:

  • Children.
  • Teenagers.
  • Adults.
  • General audience.

This information is important because applications intended for children may have additional policy requirements.

21.8.6 App Access Instructions

Some applications require users to log in before accessing their features.

If Google reviewers cannot access the application without an account, developers may need to provide valid testing credentials and instructions.

For example:

Username: reviewer@example.com
Password: [securely provided test password]

The credentials should belong to a test account, not a real user's personal account.

Why are these declarations important?

They help Google:

  1. Understand the application's functionality.
  2. Evaluate its privacy practices.
  3. Check whether it follows developer policies.
  4. Determine its intended audience.
  5. Review its use of sensitive permissions.
  6. Protect users from misleading or unsafe applications.

Google explains these declarations in its official Prepare your app for review guidance.

21.9 Testing Tracks in Google Play Console

Before making an application available to everyone, developers can distribute it to selected users for testing.

Google Play Console provides different testing tracks.

Definition:

A testing track is a distribution channel that allows developers to share application versions with testers before or during wider release.

There are four important tracks:

  1. Internal testing.
  2. Closed testing.
  3. Open testing.
  4. Production.
21.9.1 Internal Testing

Internal testing is used to share an application with a small group of trusted testers.

For example, a developer may share an application with:

  • Project team members.
  • Friends.
  • Teachers.
  • Classmates.

They can install the application and report problems.

Example:

You develop a student management application. Before sharing it publicly, you want your five team members to test the login and attendance features.

You can use internal testing.

Main purposes:

  • Find early errors.
  • Test basic functionality.
  • Check installation.
  • Get quick feedback.
  • Verify application behavior.
21.9.2 Closed Testing

Closed testing allows developers to share an application with a selected group of testers.

The developer controls who can participate.

For example, you may invite 30 university students to test your application.

They can:

  • Install the application.
  • Use its features.
  • Report errors.
  • Suggest improvements.
  • Provide private feedback.

Closed testing is especially important for new personal developer accounts because Google currently requires eligible accounts created after November 13, 2023, to complete a specific closed-testing requirement before applying for production access.

That requirement is at least 12 testers continuously opted in for 14 days. Meeting it allows the developer to apply for production access; it does not automatically guarantee approval.

21.9.3 Open Testing

Open testing allows a wider group of users to participate in testing.

Users can join the testing program through its Google Play testing page, subject to the developer's testing configuration.

For example, if you want hundreds of interested students to test your application, you may use open testing when it is available to your account.

Main purposes:

  • Collect feedback from more users.
  • Identify problems on different devices.
  • Test application performance.
  • Improve the user experience.

For eligible new personal developer accounts, open testing becomes available after production access is granted.

21.9.4 Production

Production is the track used to release an application to the general public.

After the required setup, testing, and review processes, developers can make their applications available to users.

Example:

When your student management application is ready for public use, you release it through the production track.

Users can then find and install it according to its country, device, and availability settings.

Difference Between Testing Tracks
Track Purpose Audience
Internal testing Quick initial testing Small trusted group
Closed testing Controlled testing Selected testers
Open testing Wider testing Users who join the test
Production Public release General users
Important:

These tracks are not simply four mandatory steps for every developer. Their availability and requirements depend on the developer account and the application's publishing situation.

For more information, see Google's official Testing tracks guide.

21.10 Application Review and Approval

After submitting an application, Google Play reviews it before making it available through the selected release process.

Definition:

Application review is the process of checking an application to determine whether it follows the platform's requirements and policies.

Google may evaluate:

  • Application functionality.
  • Security.
  • User data handling.
  • Privacy policy.
  • Store listing information.
  • Content rating.
  • Permissions.
  • Target audience.
  • Developer policy compliance.
What happens during the review?

Step 1: Application submission

The developer submits the application or release through Play Console.

Step 2: Automated checks

Google's systems perform checks on the submitted package and related information.

Step 3: Policy review

The application may be reviewed for compliance with Google Play policies.

Step 4: Review result

The application may receive different outcomes.

  • Approved: The release can proceed according to its release settings.
  • Rejected: The application does not meet one or more requirements.
  • More information required: The developer may need to provide additional information or correct issues.
Why can an application be rejected?

Some common reasons include:

  1. Violating Google Play policies.
  2. Misleading application descriptions.
  3. Incorrect privacy declarations.
  4. Unnecessary or improperly used permissions.
  5. Inappropriate content.
  6. Broken application functionality.
  7. Incomplete reviewer access instructions.
What should developers do after rejection?

If an application is rejected:

  1. Read the rejection explanation.
  2. Identify the specific problem.
  3. Correct the application or its listing.
  4. Update the required declarations.
  5. Upload a corrected release if necessary.
  6. Submit it again for review.
Important:

App approval is not guaranteed simply because an AAB file uploads successfully. Uploading and policy approval are separate steps.

21.11 Releasing an Application on Google Play

After completing the necessary testing, setup, and review requirements, the developer can release the application through the production track.

Steps

Step 1: Open Google Play Console

Sign in and select your application.

Step 2: Open Production

Navigate to:

Test and release → Production

Step 3: Create a production release

Select the option to create a new release.

Step 4: Upload the release package

Upload the signed AAB file if required for the application.

Step 5: Add release notes

Explain what is included in the release.

Example:

Version 1.0

- Added student registration.
- Added attendance management.
- Added result checking.
- Improved application performance.

Step 6: Review the release

Check the package, release details, and any outstanding requirements.

Step 7: Submit for review

Submit the release for Google's required review process.

Step 8: Make the release available

After the required approval and release conditions are met, the application becomes available according to the configured rollout and availability settings.

What is a staged rollout?
Definition:

A staged rollout is a release method in which an application update is distributed gradually to a percentage of eligible users instead of being made available to everyone immediately.

For example:

  • First, release to 10% of users.
  • Monitor crashes and problems.
  • Increase the rollout if everything works correctly.
  • Eventually make it available to all eligible users.

This reduces the risk of distributing a faulty update to the entire user base at once.

21.12 Application Updates and Maintenance

After publishing an application, developers must continue maintaining it.

Definition:

Application maintenance is the process of improving an application, correcting errors, updating its features, and keeping it compatible with supported devices.

Why are application updates necessary?
  1. Fix application errors.
  2. Improve security.
  3. Add new features.
  4. Improve performance.
  5. Support newer Android versions.
  6. Improve user experience.
  7. Respond to user feedback.
Steps for publishing an update

Suppose your application is currently at version 1.0.

You want to add a new attendance feature and fix a login problem.

The process is:

Step 1: Modify the application code.

Step 2: Test the updated application.

Step 3: Increase the version code and update the version name.

For example:

versionCode 2
versionName "1.1"

Step 4: Generate a new signed Android App Bundle.

Step 5: Upload the new bundle to Google Play Console.

Step 6: Add release notes.

Step 7: Submit the update for the required review.

Step 8: Release the update.

Users can receive the new version through Google Play.

Example of application version updates
Version Changes
1.0 Initial application release
1.1 Fixed login errors
1.2 Added attendance management
2.0 Introduced a redesigned interface and new features
What is application maintenance?

Application maintenance is not limited to releasing new features. It also includes monitoring application quality, handling user complaints, fixing security problems, and ensuring compatibility with new devices.

21.13 Alternative Android App Stores

Google Play Store is not the only platform for distributing Android applications.

Developers can also use alternative app stores.

Definition:

An alternative app store is an application distribution platform other than Google Play Store.

21.13.1 Samsung Galaxy Store

Samsung Galaxy Store

An application store developed by Samsung. It distributes applications, games, themes, and other digital content, particularly for Samsung devices.

Official website: Galaxy Store

21.13.2 Amazon Appstore

Amazon Appstore

An application distribution platform operated by Amazon. Developers can distribute supported Android applications through its ecosystem.

Official website: Amazon Appstore

21.13.3 Huawei AppGallery

Huawei AppGallery

Huawei's application distribution platform. It is used to discover and install applications on supported Huawei devices and other supported environments.

Official website: Huawei AppGallery

21.13.4 Xiaomi GetApps

Xiaomi GetApps

An application distribution platform available on supported Xiaomi devices and in supported markets.

Why do developers use alternative app stores?
  • Reach users outside Google Play.
  • Distribute applications to specific device users.
  • Reach additional markets.
  • Use different distribution opportunities.
  • Support devices that do not include Google Play services.
Limitations of alternative app stores
  • They may have smaller user audiences.
  • Their publishing processes differ.
  • Their policies and technical requirements may differ.
  • Developers may need to manage multiple store listings.
  • Application updates may need separate management.

21.14 Important Google Play Publishing Requirements

Google Play publishing requirements can change over time. Developers should check the current requirements before submitting an application.

Some important requirements include:

21.14.1 Target API Level

An Android application specifies a target API level to indicate the Android version and behavior requirements it is designed for.

As of November 2026, Google Play requires new applications and updates to target Android 16 (API level 36) or higher, with specified exceptions for certain device categories.

21.14.2 Privacy and Data Safety

Developers must accurately disclose the application's data collection and sharing practices.

21.14.3 Application Permissions

Applications must follow the rules for sensitive permissions, such as:

  • Camera.
  • Location.
  • SMS.
  • Contacts.
  • Microphone.
21.14.4 Testing Requirements

Eligible new personal developer accounts must complete the required closed-testing process before applying for production access.

For the applicable accounts, this means at least 12 testers must remain opted in continuously for 14 days.

21.14.5 Developer Policies

Applications must comply with Google's requirements for security, user data, content, advertisements, and application functionality.

Important:

These are platform requirements, not optional recommendations. Always consult the official documentation because requirements can change.

21.15 Advantages and Disadvantages of App Store Deployment

Advantages

1. Wider Audience

Applications can reach a large number of users through app stores.

2. Easy Installation

Users can find and install applications through a familiar platform.

3. Application Updates

Developers can distribute new versions to existing users.

4. User Reviews

Developers can receive ratings, suggestions, and complaints.

5. Application Discovery

Users can discover applications through search, categories, and recommendations.

6. Monetization

Developers can earn revenue through supported paid downloads, subscriptions, and in-app purchases.

7. Centralized Distribution

Developers can manage application releases through one platform.

Disadvantages

1. Review Process

Applications may require review before release, which can delay publication.

2. Store Policies

Developers must follow the platform's rules.

3. Competition

Many applications compete for users' attention.

4. Developer Costs

Some app stores require registration fees or impose other commercial requirements.

5. Application Rejection

Applications may be rejected if they violate store policies.

6. Maintenance

Developers must regularly update their applications.
